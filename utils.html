On Software "Utilities"

Often times we find ourselves thinking in terms of "utilities". We have, for example, the great and competing lodash and underscore "utility" libraries, which have a bunch of "utilities". We also routinely include in our project a "utils" folder and put in there a bunch of utilities. And that's about it, not too much thought goes on about it.

The Problem

Why is this a problem? The problem is that we are creating a junk drawer without a clear mental model. Utilities (as we typically use them) are anything which is used, regularly or not. The problem is that we are not keeping our code organized and clean. We are not using our mental powers to create useful abstractions. Instead we are just creating a pile of dirty laundry and keeping it as a pile.

What does utility mean? It means something *useful*. It means something that you *use*. In essence, it is an action thing. Just like we don't have a folder called "stuff" in which we put everything *except* utils, we shouldn't have a folder called "utils" where we put everything except "stuff". Why do we create folders called "components" or "views" or "models"? Because it scopes them down into what they actually are. It gives us a better mental model of what we can do with these "objects".

The problem with the utils folder is essentially it is a junk drawer. Everything goes into it that doesn't fit into nice categories. But the reality is, these utils are just actions, and so should be called such.

The Solution

The solution is, we should create an "actions" folder instead of a "utils" folder. Utils are always "actions". Actions aren't events, they are just functions that you use in your app, plain and simple. You have string actions like reversing, changing case, etc., array actions like reversing, sorting, uniqueifying, etc. You have object actions, and action actions and boolean actions like "isFunction". And in that folder, we should put only actions. Which is the bulk of our application. In fact, almost everything in a JavaScript application that is NOT a DSL is an action. This just means you need to organize your actions, like you would tools in a toolchest. You put your authentication actions here, your render or graphic actions here, your REST API actions here, etc. And you thoroughly unit test your actions, rather than leaving them as utils which often go ignored. In essence, I propose thinking in terms of "actions" as first-class citizens in the application, rather than utils. In fact, you should never have a utils folder (a junk-drawer folder). You should instead have a clean "actions" folder.

What do you gain from this approach? You gain a new layer of abstraction, the "actions". With this layer of abstraction, you can do all sorts of things. You can create an "action caller" module, which calls your actions in your app, like you would when implementing a test runner, or a redux state machine. You can then trace and more easily debug and validate these actions however you like. In fact, you don't have to import a bunch of random imports, you can import your actions and be done with it. You can also do it differently and have actions be grouped into "plugins" which you add to a global action caller module, like your API module. With this, actions can have a standard first-class pattern which is easily mockable and unit testable. In addition, it cleans up the abstraction, getting rid of your junk drawer of code.

Getting Started with Actions

What you should first do is rename all your utils folders to "actions". Then you should organize the actions into clear categories. In reality, actions can even be abstracted out into a third-party library or open source project if they are general enough. If not, then they should still likely be accessible from anywhere in the app. Then after you've renamed your utils folder to "actions", remove all your imports and replace the with a single line like `import actions from './actions'`. Replace your utils usage with `actions.doX`. Make sure all of your actions start with a verb! Actions are verbs. Finally, if you would so like, make it so your tests and QA can call these actions directly in a simple API or DSL Then you have one unified "action" system for your entire team end-to-end.
