On Software "Utilities"

Often times we find ourselves thinking in terms of "utilities". We have, for example, the great and competing lodash and underscore "utility" libraries, which have a bunch of "utilities". We also routinely include in our project a "utils" folder and put in there a bunch of utilities. And that's about it, not too much thought goes on about it.

The Problem

Why is this a problem? Utilities are often things which don't seem to be classifiable into anything else other than "utils". But what are utilities? They are usually "actions". We reserve (and do the same anti-pattern with a "consts" folder) the utils folder for essentially "actions". You have string actions like reversing, changing case, etc., array actions like reversing, sorting, uniqueifying, etc. You have object actions, and action actions and boolean actions like "isFunction".

What does utility mean? It means something *useful*. It means something that you *use*. In essence, it is an action thing. Just like we don't have a folder called "stuff" in which we put everything *except* utils, we shouldn't have a folder called "utils" where we put everything except "stuff". Why do we create folders calld "components" or "views" or "models"? Because it scopes them down into what they actually are. It gives us a better mental model of what we can do with these "objects".

The problem with the utils folder is essentially it is a junk drawer. Everything goes into it that doesn't fit into nice categories. But the reality is, these utils are just actions, and so should be called such.

The Solution

The solution is, we should create an "actions" folder instead of a "utils" folder. And in that folder, we should put only actions. Which is the bulk of our application. In fact, almost everything in a JavaScript application that is NOT a DSL is an action. This just means you need to organize your actions, like you would tools in a toolchest. You put your authentication actions here, your render or graphic actions here, your REST API actions here, etc. And you thoroughly unit test your actions, rather than leaving them as utils which often go ignored.

In essence, I propose thinking in terms of "actions" as first-class citizens in the application, rather than utils. In fact, you should never have a utils folder (a junk-drawer folder). You should instead have a clean "actions" folder.

What do you gain from this approach? You gain a new layer of abstraction, the "actions". With this layer of abstraction, you can create an "action caller" module, which calls your actions in your app, like you would when implementing a test runner, or a redux state machine. You can then trace and more easily debug and validate these actions however you like. In fact, you don't have to import a bunch of random imports, you can import your actions and be done with it. You can also do it differently and have actions be grouped into "plugins" which you add to a global action caller module, like your API module. With this, actions can have a standard first-class pattern which is easily mockable and unit testable. In addition, it cleans up the abstraction, getting rid of your junk drawer of code.
